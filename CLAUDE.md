# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` is the canonical contributor guide (structure, coding style, testing, commit conventions, security). Read it too — this file covers the architecture and commands that need cross-file context to grasp.

## Commands

Backend (Go 1.27):
- `make build` — bundles the SPA (`make web-build` → `web/dist`, embedded via `go:embed`) then compiles `standalone`, `api`, `hub` and `agent` into `bin/`, all static (`CGO_ENABLED=0`). A bare `go build` embeds whatever is in `web/dist` — the committed placeholder on a fresh checkout, i.e. an API-only binary.
- `make standalone | api | hub | agent` — `go run` the chosen binary.
- `make lint` — `go vet ./...` plus the web ESLint suite.
- `go test ./...` — all tests. Single package: `go test ./internal/infra/transport/codec/`. Single test: `go test ./internal/infra/orchestrator/docker_compose/ -run TestAggregateStatus`.
- `make test-pg` — the API contract suite (`internal/app/web/contract`) and the `internal/infra/db` packages (migration runner, repositories) on a throwaway `postgres:16` container; `go test ./...` runs them on SQLite. Every table route must answer one of its calls below 400 (the `TestMain` guard fails otherwise; CI sets `WF_CONTRACT_GUARD=require` so a `-run`/`-skip`/`-short` run fails instead of skipping the guard); `TestParity`'s golden (`-update`) must match on both databases. Locally `make diffcov` sees SQLite coverage only; CI merges the Postgres contract profile, which is the only coverage of Postgres-only branches. The ratchet baseline (`coverage-baseline.json`) is calibrated to that merged SQLite+Postgres profile, so a local SQLite-only `make cover` can report below it without a real regression; reproduce CI with the merged profile: `make test && make test-pg TEST_PG_ARGS='-race -covermode=atomic -coverpkg=./... -coverprofile=contract-postgres.out' && tail -n +2 contract-postgres.out >> coverage.out && make web-test`, then `go run ./tools/diffcov ratchet --go coverage.out --lcov web/coverage/lcov.info` (or `go run ./tools/diffcov --base main --min 80 --go coverage.out --lcov web/coverage/lcov.info` for the diff gate).
- `make generate-hub-certs` / `make generate-agent-certs` — bootstrap local mTLS material (agent certs depend on hub certs existing first).
- `make grpc` — regenerate Go from `internal/infra/transport/grpc/proto/hub.proto` (installs `protoc-gen-go`/`protoc-gen-go-grpc`).
- `make sqlc` — regenerate `internal/infra/db/sqlc/gen` (packages `sqlitegen`, `pgsqlgen`) from the per-engine queries and migrations; sqlc is pinned and run through `go run` (needs a C compiler). `make sqlc-check` fails when the committed code is stale (CI's `sqlc` job).
- `go run ./cmd/catalog build --apps <winterflow-apps checkout> --out <dir> --base-url <https url> [--sign-key-env NAME] [--source-commit SHA]` — build the catalog feed (see **Catalog**); `go run ./cmd/catalog keygen` prints a signing key pair.
- `make openapi` — regenerate `api/openapi.yaml` from the route tables (`go run ./cmd/openapi`); `TestOpenAPIUpToDate` fails until it is committed.
- `make release-binaries` — cross-compile `winterflow-{standalone,agent,api,hub}-linux-{amd64,arm64,arm}` plus `SHA256SUMS` into `release-out/` (the web is built twice: the standalone binary embeds the standalone SPA, the api binary the `VITE_APP_MODE=distributed` one). `make cdn-upload CHANNEL=<vYYMMDD.N|latest>` mirrors `release-out/` to R2 (`s3://econumo/winterflow/<channel>/`, econumo's bucket; `R2_BUCKET` overrides) with the aws CLI; needs `WINTERFLOW_R2_ENDPOINT` (`https://<account_id>.r2.cloudflarestorage.com`), `WINTERFLOW_R2_ACCESS_KEY_ID`, `WINTERFLOW_R2_SECRET_ACCESS_KEY`. The release workflow runs it for the version and `latest` from the GitHub secrets `R2_ENDPOINT`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` and skips with a warning when the endpoint is absent.
- Installers (`scripts/`, each self-contained so it works piped from curl; every shared helper block is copied into each and `shared_helpers_test.sh` fails when the copies differ): `install.sh` (standalone, SQLite; the only one the README names), `install-agent.sh` (agent: generates the key + CSR, enrolls, prints the code, starts the unit only once claimed; a rerun keeps an existing enrollment unless `--reenroll`, which stops the unit and sets the cert, key, CA and agent.env enrollment lines (and `hub.json`) aside as `*.old-<timestamp>`; reached as `get.winterflow.dev/agent`), `install-control-plane.sh` (Postgres, a dedicated TLS Redis, API and hub on one Debian/Ubuntu host from R2; see `docs/install-control-plane.md`), `install-hub.sh` (a hub alone on another host, from R2: `--token`/`WINTERFLOW_HUB_TOKEN`, `--public-addr`, `--redis-url`/`WINTERFLOW_HUB_REDIS_URL` (rediss only), runs `winterflow-hub join`; a rerun updates, `--uninstall` drains first, `--purge` also removes certs and env; refuses control-plane hosts). Tests, all `--dry-run`/`WF_INSTALL_ROOT` based and rootless: `bash scripts/install_test.sh`, `install_agent_test.sh`, `install_control_plane_test.sh`, `install_hub_test.sh`, `shared_helpers_test.sh`, `release_test.sh` (Makefile/workflow release contract). Run all of them after editing any script.

Frontend (`web/`, pnpm + Vite + React 19):
- `make web` (= `pnpm --dir web dev`), `pnpm --dir web run build` (runs `tsc -b` first), `pnpm --dir web run lint`.

**The web UI ships inside the Go binary** (econumo-style): `web/embed.go` does `go:embed all:dist` and `internal/app/web/spa` serves it as the router's NotFound handler with SPA history-mode fallback (reserved prefixes `/api`, `/auth`, `/avatar`, `/_` still 404; missing extensioned paths 404 instead of returning the shell). Production bundles are same-origin: `web/.env.production` pins empty `VITE_*_BASE_URL`s (→ `window.location.origin` in `web/src/config.ts`) and `VITE_APP_MODE=standalone`; the api Dockerfile builds with `VITE_APP_MODE=distributed`. Keep `web/dist/.gitkeep` committed — the placeholder is what makes a frontend-free checkout compile (and `DistFS()` report "no build").

Config comes from `.env` (loaded via `godotenv`) or the process environment. Copy `.env.example` → `.env` (frontend build-time vars: `web/.env.example`). `.env`, `data/`, `bin/`, and `*.sqlite*` are gitignored.

**`.env.example` is the canonical, commented inventory of every env var the backend reads.** Whenever you add, rename, remove, or change the default of an env var in Go (any `os.Getenv`/`os.LookupEnv`, normally via a `pkg/config` getter), update `.env.example` in the same change — variable, default, and a comment saying what it does and which topology reads it. The installer's generated config (`scripts/install.sh`) points users at it, so a stale example is user-facing. Same rule for frontend `VITE_*` vars and `web/.env.example`.

## Architecture

This is the **v2 monorepo** that merges the v1 `winterflow-agent` and `winterflow-app` into one codebase producing four binaries. The same business logic serves two topologies; the only thing that differs is how commands are transported.

**Topologies (this is the central design):**
- **Standalone** (`cmd/standalone`, `config.NewServerConfig("standalone")`): one process running the HTTP API, the agent, and the Docker Compose orchestrator over SQLite. The "bus" and "hub" run in-process — there is no Redis or gRPC hop.
- **Distributed** (`config.NewServerConfig("distributed")`): horizontally-scalable **API** (`cmd/api`, the "brain", owns persistence) ⇄ **Redis Bus** ⇄ horizontally-scalable **Hub** (`cmd/hub`, gRPC server with mTLS) ⇄ **Agent** (`cmd/agent`). The API publishes a command to the request queue; the Hub forwards it down the addressed agent's gRPC stream; the agent's reply travels back up onto the response queue, where the API's `reply.Manager` wakes the blocked caller.

**The command round-trip** (trace this to understand the whole system):
1. HTTP handler (`internal/app/web/handler/`) → usecase (`internal/domain/usecase/`) → `port.AppService.SaveApp(...)` with a result callback.
2. The service implementation (`internal/infra/transport/redis/service/app`, type `BusAppService` — bus-agnostic despite the package path) publishes a `bus.CommandMessage` keyed by a `request_id` and registers a reply channel.
3. The Hub (`internal/infra/transport/grpc/hub`) consumes the request queue via `StartBusBridge`, looks up the agent stream, and sends a `proto.RequestEnvelope`. In standalone, `internal/app/agent/inprocess.go` (`InProcessBridge`) does the same in-memory.
4. The agent's `Dispatcher` (`internal/app/agent`) decodes the envelope, runs the Docker Compose orchestrator, and returns a `proto.ResponseEnvelope`.
5. The Hub/bridge publishes the result as a `model.Notification{Ref: request_id, ...}` onto the response queue; the API's bus subscriber routes it to `reply.Manager.Publish(ref, ...)`, unblocking step 2's callback, which then publishes to the shared `NotificationManager` (SSE → browser).

**Single gRPC envelope + typed commands** (the deliberate simplification over v1's ~14 oneof RPC pairs): all hub↔agent traffic rides one envelope (`proto.RequestEnvelope`/`ResponseEnvelope` = a `type` string + JSON `payload`). The catalog of command types and payload structs lives in `internal/domain/command`; `internal/infra/transport/codec` is the ONLY place that (de)serializes payloads. **To add a feature:** define a command type + payload struct in `internal/domain/command`, add one registration line in the agent Dispatcher's `newHandlers` map (`internal/app/agent/dispatcher.go`) plus the orchestrator method, and add a usecase/handler + route on the API side. Routes live in typed tables: each handler package's `Routes(g api.Guards) []api.Route` (`internal/app/web/api`) is both what `routes.go` registers with chi (`api.Register`, fail-closed on nil guards) and what `internal/app/web/api/openapi` renders into `api/openapi.yaml`; `api.Guards` carries only the per-IP rate limiters (`g.AuthLimit` for bcrypt-priced endpoints, `g.EnrollLimit` for the enrollment refresh/status polls, `g.EnrollStartLimit`, about 3 a minute with burst 5, for enrollment start) — there is no role guard. Run `make openapi` after any route or response-type change. Response-side schemas require every non-`omitempty` field and allow `null` for nil-able kinds; a type also used in a request body gets a separate lenient `<Name>Input` component. A new SSE notification type needs an `api.EventPayload` entry in `handler/notification/routes.go`. Add a contract test in `internal/app/web/contract` (happy path, plus a `probes` entry when the route takes input).

**Implemented command surface** (the v1→v2 migration is complete for these): app lifecycle — `app.save` (create/edit, new revision + redeploy), `app.get`, `apps.list` (reconcile), `apps.status`, `app.control` (start/stop/restart/update), `app.delete` (optional `delete_volumes` also removes the app's named volumes, `delete_backups` its backups), `app.rename`, `app.logs`; Docker resources — `registry.list/create/delete`, `network.list/create/delete`, `volume.list/create/delete`; ingress — `domain.list/create/delete` (registered domains, see below); storages — `storage.list/test/save/delete/orphans/delete-orphan` (see below); backups — `backup.update/points/run/restore/delete-point` (see below); shared variables — `vars.sync` (a server's full snapshot), `vars.reload` (re-render + compose up of stale running apps, queued on a worker; per-app outcomes arrive as `vars.reloaded` agent events; with exactly one `app_ids` entry it waits for that app's outcome, at most `command.ReloadAppWait`, which is why `vars.reload` is a detached command); agent — `agent.update` (self-update); host — `process.list` (Monitoring's Processes tab, polled only while it is open; `/proc` reads, disk I/O per container or service from cgroup `io.stat`, no extra capability). All are agent-bound; their routes answer 202 + `request_id` (result over SSE), except the shared-variable routes, which answer 200 once the DB write commits (sync outcomes arrive as `vars.*` SSE events, reloads as `rollout` events).

**Registered domains:** every ingress hostname must be covered by a domain registered on the same server (`{AGENT_DATA_DIR}/domains/`, mirrored into the API's `server_domains`): an exact name or `*.suffix` (one label; exact wins), each with a TLS mode — `auto` (ACME per host), `certificate` (uploaded PEM pair, key ECIES-encrypted like registry passwords, loaded via `load_files`) or `off` (plain HTTP behind a tunnel/proxy). The ingress `ssl` flag is ignored. `save-app` 400s on uncovered or per-server-duplicate hosts; the agent excludes uncovered hosts again in `BuildConfig`. The first start without `domains/` registers existing hostnames once (`ssl:true` → auto, else off).

**Shared variables:** org- and server-level variables and secrets (`shared_variables`, `shared_secret_ciphertexts`, `servers.vars_revision`; routes `/api/v1/org|server/*-shared-variable*`, `/api/v1/shared-variables/resync|reload`). Precedence built-ins < org < server < app; `COMPOSE_PROJECT_NAME` and `WF_*` are reserved; `WF_*` built-ins are agent-computed. Secrets use browser fan-out: one ECIES ciphertext per keyed server, the API never sees plaintext; a server key change purges that server's copies. The API pushes the full snapshot as `vars.sync` on save/delete, agent connect and revision drift (`apps.status` carries `vars_revision`); the agent stores `{AGENT_DATA_DIR}/vars/snapshot.json` (0600, ciphertext only) and renders only referenced names into the gitignored `.env.shared` / `.env.shared.secrets` (0600) on the paths that call `materializeSecrets`, never on sync. Compose env files (composeArgsFor and run.sh): `.env.shared .env.shared.secrets .env .winterflow/storage.env .env.secrets`. Stale apps ride `apps.status` as `stale_vars`; reloads run on one worker goroutine under the per-app operation lock and register with `beginOp` (refused while a restore runs). The API never sends a bulk `vars.reload` any more: `reload: true` on save/delete and `POST /api/v1/shared-variables/reload` queue or extend the org's `vars_reload` rollout (see **Rollouts**), which reloads the stale running apps one at a time with the single-app form.


**Storages:** a storage is a local folder or an S3-compatible bucket registered per server (`{AGENT_DATA_DIR}/storages/<name>.json`, 0600, secret ECIES-encrypted at rest; mirrored without secrets into the API's `server_storages`). Drivers live in `internal/infra/backup/store` (`local`, `s3` via minio-go); every save runs the 30s probe test first. Compose files reference storages as `${WF_STORAGE_<NAME>_<FIELD>}`: only referenced values are materialized at every deploy into the gitignored, never-committed `.winterflow/storage.env` (passed between `.env` and `.env.secrets`; the shared files come before `.env`); user variables may not start with `WF_STORAGE_`/`WF_BACKUP_`; save-app 400s on a reference to a missing storage. Compose files are always passed with explicit `-f` (`composeFiles`, compose's own detection order plus override), and `run.sh` mirrors the flags. `storage.save` redeploys the running apps that reference it (stopped apps and drafts are left alone); `storage.delete` is refused while an app references it. A deploy is refused while a referenced local storage's folder is missing (10s-bounded stat, so docker never creates a bind source on the system disk); under `/mnt` and `/media` a folder on the same filesystem as `/` (an unmounted mount point) is refused too.

**Backups:** a compose file declares what can be backed up under `x-winterflow.backups` (the recipe: `sqlite`, `files`, `custom`; parsed and validated by `internal/domain/backup/recipe`, shared by the API's save-app 400s and the agent); per-deployment settings (on/off, storage, schedule, paths, UI-added backups) are overrides in the committed `.winterflow/config.json` → `backups`, replaced as a whole by `backup.update` and kept across app-editor saves (`keepBackups`). `${WF_BACKUP_<NAME>_<FIELD>}` resolves to the backup's storage (PREFIX narrowed to `<app-id>/<backup>/`, empty while off); an enabled `custom` backup activates the compose profile `wf-backup-<name>` (passed with the user's `COMPOSE_PROFILES` as `--profile`; a disabled one's service is removed with `rm -fs`, since `up --remove-orphans` leaves it). The agent runs `sqlite`/`files` backups itself: the scheduler (`internal/app/agent/backup`, one goroutine, one timer, one run at a time, `{AGENT_DATA_DIR}/backups/state.json`) calls `RunBackup`, which mounts the app's own volumes/binds (resolved from one cached `docker compose config`) into a capped `alpine:3.20` helper running this binary's hidden `backup dump` subcommand (the binary must be static, `CGO_ENABLED=0` as `make build`, `scripts/install.sh` and goreleaser build it: alpine has no glibc loader, and the agent refuses to run a backup from a dynamic ELF; `internal/app/backup/cli`, exit 3 unchanged / 4 missing), zstd-compresses its stdout to the storage with a manifest written last (`internal/infra/backup/layout`), then prunes by tiers under `BACKUP_RETENTION_DAYS`. `backup.run` is a detached command: the in-process bridge runs it off its single goroutine, and the API awaits its result for 2h (`DispatchInput.Wait`; the agent bounds the wait the same, and a stopped scheduler fails it at once). Health rides on `apps.status` (`AppStatus.Backups`). `backup.restore` is detached too and runs on the same scheduler (never beside a backup): `RestoreBackup` downloads the point to `backups/tmp` and checks its sha256, stops a running app, saves the current data as a `pre-restore` point (a run; its failure aborts and starts the app again), then a helper with `CHOWN`/`FOWNER` runs `backup restore` — sqlite replaces the file (quick_check, owner and mode kept; the old `-wal`/`-shm`/`-journal` are set aside as `*.restore-old`), files extracts into `.wf-restore-<id>/` at each mount root (free space checked, `..`/absolute/outside/through-symlink entries refused) and swaps only the backup's paths. Only a clean helper failure (exit 1, docker's 125-127), or a files helper stopped from outside before its `{"phase":"swapping"}` stderr line (only when its container is confirmed removed, the docker CLI ended by itself with its output read in full, and no `.wf-restore-<id>.old` is on a bind mount), leaves the data as it was and starts the app again (unless the scheduler's `Forget` cancelled it with `ErrAppDeleted`); any other end (a crash, a kill, exit 5, a swap that failed, an agent stop) leaves the app `compose down` (never `-v`) and the error names the pre-restore point, for sqlite too. A manifest records the copy's `entries`; a copy of a location the backup no longer has is refused. The restore's time is checked against the copy's raw size before the app is stopped and again after the pre-restore copy. `backups/restoring.json` records restores in progress: after an agent stop (it is kept past a restore a plain cancel left in doubt, and that restore's error is also stored as `last_error`), the next start turns it into the backup's `last_error`, and `agent.update` is refused while a restore runs. A restore (or run) that outlives its deadline gets `RestoreStopBudget` (derived from the engine's own cleanup bounds) before the scheduler abandons it, and its final outcome is logged and kept as `last_error`. The scheduler nudges the status reporter (`Changed()`) when a run ends or the plan is reread, so health reaches browsers at once. A per-app file lock (`lockApp`, reference counted, held for file work and one commit only) makes `backup.update`'s base check and commit one step, shared with save, rename, rollback and the source poll's commit; clone/fetch of a git-sourced app's upstream runs under a lock of its own (`lockSource`), before a save takes the app lock. Deleting an app marks its backup folders `<app-id>/.deleted` (or purges them with `delete_backups`); the scheduler's daily sweep applies `BACKUP_RETENTION_DAYS` to marked folders only, and `storage.orphans`/`delete-orphan` list and delete the folders of apps not on this server.
 Two per-app locks exist: the **operation lock** (`applock.go`: `lockForMutation`, held for a public mutator's whole run — save, start/stop/restart/update, delete, rollback, rename, `backup.update`, storage redeploys, the source poll — giving up after 30s with `ErrAppBusy` so the standalone bridge never wedges; the reload worker waits ctx-bounded) and the file lock above. Order: operation lock → `beginOp`/`beginRestore` → `lockApp` → `lockSource` → `sharedMu` (a save or source poll releases `lockSource` before taking `lockApp`; only a rollback holds both). A restore never takes the operation lock; `beginRestore`/`beginOp` exclude it from the mutators and reloads.

**Templates and instances (API only; the agent never sees a template):** a template is an org's own (`templates.source` `org`, editable) or the catalog's (`catalog`: `org_id` NULL, a unique `slug`, `withdrawn_at` once the feed drops it; read-only to every org, so save-template and delete-template answer 403 `model.ErrCatalogReadOnly`, class `model.ErrForbidden`; written only by the catalog sync, see **Catalog**), with immutable revisions (`template_revisions`, a catalog one with its `digest`). Every read is scoped: an org reads its own templates and every catalog template (`get-templates` lists its own first; a withdrawn one only while the org has live instances of it, and it takes no new installs, `model.ErrTemplateWithdrawn`). A body is `files` plus `summary`, `description`, `icon`, `color`; what an instance fills in, which ports it exposes and which backups it can turn on come only from the compose files' `x-winterflow` block (`template.Parse`, `ModeTemplate`: a non-external volume with a literal `name:` is an error). `template.Validate` checks a save (a compose file, file paths, the metadata limits, the shared parser, the backup recipe; the body ≤1 MiB; undeclared `${VAR}`s in the compose files only warn: compose interpolates nothing else); `get-template` returns what the revision declares as `detected` (variables, expose entries with their targets, backups, warnings), and `POST /api/v1/template/inspect-template` reads a body the same way without storing it (the editor's Detected panel; a body a save would refuse answers 200 with its `problem`). An instance (`template_instances`) is an ordinary app rendered by `template.Render` into the `app.save` payload the editor would send (files unchanged; one app variable per given value, so a declared variable without one keeps the compose file's literal; secrets as the caller's ECIES ciphertext or the `<encrypted>` keep placeholder; a config blob with the app name, the instance's `hosts` as its ingress, `template_id` and the `instance` marker, and no `ports`, so the agent keeps the app's host ports) and dispatched through the app usecase's `CheckSave` + `DispatchSave`, so every save-app check applies before anything is claimed. `template.Resolve` checks the values (each a declared variable, plain or secret as declared, no `$` in a plain value, a secret in the ECIES wire format's shape, then `CheckValues`; a given `""` clears a stored value); `template.CheckHosts` the hostnames (`[{host, expose}]`, each on an http expose entry). The app name is the create's `name` (default: the template's), stored on the instance; later renders use the app's current name from the API's app list (a rename sticks). The caller's `key` is unique per org among instances not unlinked (partial unique index); a create claims it only after the checks pass, a replay with the same request hash (server, template, requested revision, name, values, secret *names*, hosts, backups) is looked up before any check: it answers the created instance as stored (a later revision or a withdrawn template changes nothing) or re-dispatches a pending one at the revision and with the name it was claimed with (a withdrawn template refuses that), another request is 409, a deleted instance's key stays retired (409), unlink frees it. Updating or upgrading a pending instance renders like a create (every secret resent, the whole backups list sent: the request's `backups`, accepted only while pending, replace the instance's stored ones, else the create's stored `backups` are sent, less those the revision dropped); `hosts` on an update or upgrade replaces the stored ones. An upgrade re-renders with the stored values and hosts and sends no backups list (the agent keeps the app's settings; a backup the revision adds starts off); a newly required value missing, a stored value the revision refuses or a stored host whose expose entry the revision dropped is `templates.ErrNeedsValues` (a 400, skipped by "Upgrade all"). Instance routes take `wait: true`: the handler holds only its own request on a buffered channel fed by the dispatch result observer (which records the outcome either way; an observed dispatch keeps its result for `appuc.ObservedResultTTL`, 15 minutes, beyond the 10-minute wait), at most 10 minutes, then answers 202; a failed command is 502 and stays as `last_error`. An instance's app is changed through its instance: save-app and rollback-app on an app a pending or created instance manages answer 409 (`port.InstanceLinks`, served by the templates repository and given to the app usecase; rename is allowed), and delete-app's success retires its instance's key like delete-instance. `POST /api/v1/template/upgrade-instances` ("Upgrade all") queues the org's `template_upgrade` rollout of the template; it also starts instances the user had stopped (an upgrade is a save, which redeploys).

**Catalog:** the catalog templates come from a signed JSON feed. `internal/domain/catalog` is its format (`Feed`/`Entry`, `FormatVersion` 1; `Digest` = `sha256:` over the files in name order, each `<len(name)>:<name><len(content)>:<content>`; ed25519 `Sign`/`Verify` over the exact `catalog.json` bytes, the `.sig` being the base64 signature and a newline) and `Entry.Check`, the one check the builder and the sync share (slug `^[a-z0-9][a-z0-9_-]{0,127}$`, name, list/license/URL limits, https URLs, the digest, then `template.Validate` and the 1 MiB cap). The builder (`cmd/catalog build`, logic in `internal/app/catalog`) reads a winterflow-apps checkout: each `apps/<slug>/` with `metadata.json` and `compose/compose.yml`, not `waiting_list` and not an agent `extension`, becomes an entry with `compose.yml` plus its `x-winterflow.files` (relative to the compose folder); every other folder is skipped and listed; any invalid app fails the build, listing every one, before anything is written; every file is read through an `os.Root` and must be a regular file (a symlink or `..` cannot leave the compose folder or `assets/`; a symlinked `compose/`, `metadata.json` or `assets/` is refused or ignored, never followed), and `--base-url` must be https without userinfo, query or fragment. It writes `catalog.json` (apps by slug, compact), `catalog.json.sig` (with `--sign-key-env`; without a key a stale `.sig` is removed) and `logos/<slug>.<ext>` copied from `assets/` (only an image extension, `.png .svg .jpg .jpeg .webp .gif .avif`, is published; no logo, a missing file or another extension is a warning): each file by a rename of a temp file beside it, logos first and `catalog.json` last, then logos the feed no longer lists are removed, so a reader never sees a half-written feed. The API syncs it (`internal/domain/usecase/catalog`, started by `bootstrap.StartCatalog` next to `StartRollouts`, one goroutine per process, never the standalone bridge's): a minute after start, then every `CATALOG_REFRESH` (24h, at least 5m), each sync bounded by 5 minutes; a failed sync is retried after 5 minutes, doubling up to `CATALOG_REFRESH`, and the backoff resets after a success (a 304 included; `Schedule.Retry`); `internal/infra/catalogfeed` GETs `CATALOG_URL` with `If-None-Match`, then the `.sig` (30 s per request, 8 MiB / 4 KiB caps, https only, http only to a loopback host, redirects included). The whole feed is refused on a signature that does not verify against `CATALOG_PUBLIC_KEY` (compiled-in default `config.DefaultCatalogPublicKey`), an unknown format, no apps, a slug listed twice, a `generated_at` older than a feed already applied (`ErrStale`: `templates.catalog_feed_at` is stamped on every catalog template after the applies and before the withdrawals, so this holds across replicas and restarts, and an older mirror cannot un-withdraw a template) or more than an hour ahead (`ErrFuture`); an invalid entry is logged and skipped (an existing template keeps its last good revision and is not withdrawn). Each changed entry is applied in one transaction (`port.CatalogRepository.ApplyCatalog`): a new template with revision 1, a new revision only when the digest changes, else the name and `model.CatalogMeta` (`templates.catalog`; `catalog` in get-templates and get-template, null for an org template) in place; every write is conditional (the slug free, `latest_revision` still the one read, no newer `catalog_feed_at`), so a replica that loses a race, or a stale mirror, skips instead of adding a revision or rolling back. A catalog template the feed no longer lists gets `withdrawn_at` (hidden from lists and new installs, instances unaffected) and comes back when a feed lists it again; a renamed slug is a new template. The ETag is kept only after a sync fully applied, so a failed one refetches instead of reading a 304. `CATALOG_URL` empty switches the catalog off: every catalog template is withdrawn once at start.

**Rollouts:** the queue of one-app-at-a-time jobs (`rollouts`, `internal/domain/usecase/rollouts`; routes `/api/v1/template/upgrade-instances`, `/api/v1/rollout/get-rollouts|stop-rollout`; an SSE `rollout` event, a `model.RolloutView`, to the org on every change and only then; it is published by the worker's process only, so with several API replicas the step events reach browsers on the worker's replica, and pages on the others catch up through `useRollout`'s re-read of `get-rollouts` every 15 s while the shown rollout is active and the page visible). Kinds: `template_upgrade` (scope key `<org_id>:<template_id>`, `model.UpgradeScopeKey`, so two orgs upgrading one catalog template don't block each other; the API names the scope by the template id in `get-rollouts`' `scope_key` and the view; the org's oldest `created` instance below the target revision is re-rendered with its stored values through the instance update path; one whose values the revision refuses, `templates.ErrNeedsValues`, or that went away is skipped; one whose save went through but was not recorded, still below the target, counts as done and joins `skip_ids`; deleting a template deletes the org's upgrade rollouts of it in the same transaction) and `vars_reload` (scope key the org id; scope `model.ReloadScope`: names × server_ids, all_stale servers, app_ids, plus each server's `revisions` and `settle_by`; the next app is a running app whose `stale_vars` in the API's status cache the scope wants, on a server whose latest report reached the scope's revision; until `settle_by`, 5 minutes, it waits for a server that has not, then leaves it out; a step sends the single-app `vars.reload`; an app deleted while its reload was queued or in flight, gone from the API's catalog, is skipped). One active rollout per (kind, scope_key) (partial unique index): a second upgrade of a template by one org is 409, a reload extends the active one (scope merged in Go, written by one conditional UPDATE on `scope_rev`; the worker completes a rollout only at the `scope_rev` it evaluated); extending a reload whose stop was requested is refused with 409 "a reload is stopping". One worker goroutine per API process, started by `bootstrap.StartRollouts` once commands can flow (standalone: after the in-process bridge subscribed; API: after the response subscriber `WireCore` starts), not inside `WireCore` (`Deps.Rollouts` is the one value whose `Wake` reaches it): a pass on every wake and once a minute (one indexed query when idle); a 2-minute lease claimed in one statement and renewed every 30 s, every worker write naming its owner (a lost lease cancels the step in flight; another process resumes after expiry; lease comparisons are `<=`); a step picks the next app fresh, records `current_app_id`, dispatches and awaits the result (10.5 minutes), then waits (5 minutes) for the app to read healthy on two status reports received after it whose receive times are at least `healthSettle` (20 s) apart (one is not enough: a crash-looping container reads running between restarts) and counts it, skips it (`skip_ids`, never picked again) or fails the rollout naming the app. Healthy means at least one Active container, none Restarting or Problematic, the rest Active or Stopped (a finished one-shot); a report showing a Restarting or Problematic container fails the step at once, naming the container, and any other unhealthy report starts the count again; at the bound no containers, no report, a single healthy report, or an app reading Stopped or unknown fails the step (an app reading Idle for other reasons, such as a paused container beside running ones, passes); a Docker healthcheck's `unhealthy` is not seen: such a container reads running. A `vars_reload` that has no app yet but waits for a server to report (`settle_by` not reached) parks itself (no owner, `lease_until` now + 5 s) and yields the worker, so one quiet server holds neither other rollouts nor the claimable list; `Run` looks again every 5 s while one waits. `Stop` ends a rollout nobody drives (queued, parked, or an expired lease) at once; otherwise `stop_requested` stops it after the step in flight. No transaction is held while a step waits. Ended rollouts beyond the newest 20 per scope are pruned when one ends. The status cache keeps each report's receive time and `vars_revision` (`status.Cache.LatestReport`).

**Hubs and routing (distributed):** each hub writes `hub:status:<hub_id>` to Redis every 30 s with a 90 s expiry (JSON: hub_id, public_addr, capacity, connected_agents, accepting, draining, version); `hub_id` is the host part of `HUB_PUBLIC_ADDR` (`HUB_CAPACITY` default 1000, `HUB_ACCEPTING` default true). The API finds hubs with `SCAN MATCH hub:status:*` at claim time and picks a random accepting, non-draining hub whose assigned `servers` rows are below capacity (all full: the lowest assigned/capacity ratio, with a warning; none listed: the claim fails with "no hub is available", the code stays valid). `servers.hub_id` records the choice and routes every command. **Joining:** `winterflow-api hub-token [--ttl]` (run on the API host) prints a one-time join token, `wfh_` + 32 random bytes base64url (SHA-256 in `hub_join_tokens`, default TTL 1 h, single use, pruned a day after expiry). The public `POST /api/v1/hub/enroll` (behind `EnrollStartLimit`) takes the token and a CSR and returns a certificate from `SignHubCSR` (ServerAuth, `CN=<hub_id>`, SAN = the public host) plus the CA. `winterflow-hub join` (run by `install-hub.sh`) makes the key on the hub's box and does this; whoever holds the token chooses the hub's host name. **Agent migration:** `POST /api/v1/agent/hub` is signed with the agent's key (`agentsig`, payload prefix `winterflow-agent-hub-v1`, clock skew +-5 min, expired certificates refused, unknown server 401) and answers `{hub_addr, moved}`. The agent follows any differing address, persists it in `{AGENT_DATA_DIR}/hub.json`, and asks on a `hub.move` message, on `FailedPrecondition` (30 s floor between asks) and after 3 minutes without its hub; `WINTERFLOW_API_URL` names the API. `server.verify` answers `moved` (also for a NULL `hub_id`) when the server belongs to another hub, which the hub turns into `FailedPrecondition`; `SetServerHub` is a compare-and-set. **Draining:** `winterflow-hub drain|undrain` sets or deletes `hub:draining:<hub_id>` in Redis (no expiry; survives hub restarts, lost if Redis loses its data). A draining hub announces `draining` in its status, sends `hub.move` to each stream at about 20 per second with a 1-minute resend, refuses new registrations with `FailedPrecondition`, and a stop drains for at most 2 minutes (unit `TimeoutStopSec=150`); a stop with no streams, or with no other accepting, non-draining hub listed (`ErrNoOtherHub`, also once every agent was told and the last other hub left), moves nobody and does not wait.

**Agent enrollment (distributed):** `winterflow-agent enroll` (run by `install-agent.sh`) makes the key on the agent's box and sends a CSR to the public `POST /api/v1/agent/enroll`, `/enroll/refresh` and `/enroll/status` (unauthenticated, behind their own per-IP limiters; pending enrollments are capped at 1000 in all and 10 per client IP, stored as `client_ip`, Start answering 429 past the per-IP cap; table `agent_enrollments`). It gets a 6-character `code` valid 10 minutes (refresh issues a new one; the 10th is the last, the server enforces the cap) and a high-entropy `poll_secret` (hash stored). The user types the code into the UI, which calls the existing authenticated `POST /api/v1/server/register`; that claim assigns the `server_id`, signs the CSR with `CN=<server_id>` (the CSR's own subject is ignored) using the CA the API holds (the distributed API refuses to start without the CA key/cert pair; hubs hold only the CA certificate and their own pair), creates the `servers` row and picks the hub, in one transaction. The claimed result (certificate, CA, server_id, hub address) stays collectable by `poll_secret` for 15 minutes; after that status answers `uncollected` (the row is kept 2 h) and `enroll` tells the user to remove the server and rerun the installer. The claim route has a per-user attempt limit. A failed enrollment leaves the agent unit disabled and stopped. Standalone's own `AgentService.Register` path is unchanged.

**Hub identity and revocation:** on `RegisterAgent` the hub rejects an `AgentId` that differs from the verified client certificate's CN, then asks the API over `hub:requests` (`server.verify`: server id + certificate fingerprint; every API replica answers on `hub:responses:<hub_id>`, first reply per `request_id` wins, 5 s wait). Verdicts: `allowed`, `unknown` (no such server) and `revoked` (not the active certificate) mean gRPC `PermissionDenied`; no reply or a bus error means `Unavailable` (fail closed, transient). `delete-server` publishes `server.revoked` on `hub:broadcast` and the holding hub closes that stream; the stream is pinned to its cert fingerprint, one stream per agent. The agent retries `Unavailable` forever with the 1-30 s backoff but, after five `PermissionDenied` in a row, logs the reason and exits 78 (the unit's `RestartPreventExitStatus=78` leaves it stopped); any successful connection resets the count. Re-enrolling a box (`install-agent.sh --reenroll`, the command the Remove-server dialog shows) issues a new server id; the old one is never reactivated. `delete-server` answers 409 in standalone, whose one server could not be added back. None of this applies to standalone.

**Redis over TLS:** every distributed Redis client (API and hubs) goes through `NewRedisClient`: TLS and a password; `REDIS_TLS` (default true in distributed, false only for local development against the plain docker-compose Redis), `REDIS_CA_CERT_PATH` (default the Winterflow CA certificate). The control-plane installer runs a dedicated `redis-server@winterflow` (TLS only, port 6380) and never touches the distro's Redis. `API_LISTEN_ADDR` sets the API's bind address (the installer binds it to loopback behind the owner's Caddy).

**Databases and releases:** standalone defaults `DATABASE_URL` to `sqlite://winterflow.sqlite` and accepts `postgres://`; distributed requires Postgres (SQLite is refused at startup). Release assets on GitHub are `winterflow-<os>-<arch>` (standalone) and `agent-<os>-<arch>`; the old `winterflow-standalone-*`/`winterflow-agent-*` names are gone from GitHub releases (binaries installed earlier need the installer rerun once to self-update again). The R2 mirror holds all four binaries (`winterflow-{standalone,agent,api,hub}-linux-<arch>` + `SHA256SUMS`) under `winterflow/<channel>/`; the control-plane installer downloads from it with `curl --aws-sigv4` and verifies the sums.

**App secrets are ECIES-encrypted end-to-end** (`pkg/crypto`, P-256 ECDH→SHA-256→AES-256-GCM): the browser encrypts a secret with the agent's public key (served by `GET /api/v1/server/get-public-key`, sourced from the `public_key` capability or the local agent cert in standalone); the agent decrypts with its mTLS private key before render. Editing sends the `<encrypted>` placeholder for unchanged secrets (the agent preserves the stored value, never returns plaintext). Registry passwords use the same scheme.

**Agent resilience:** the agent runs a supervising `Run(ctx)` loop (`internal/infra/transport/grpc/agent`) that reconnects with exponential backoff (1s–30s) on stream loss; the Hub deletes agent registrations on stream close and reaps agents idle past a TTL (~3 missed heartbeats).

**No DI/factory** — there is intentionally no factory abstraction (an earlier `AppFactory` was removed). Each binary wires its concrete dependencies explicitly in `internal/infra/bootstrap` (`BootstrapStandalone`/`BootstrapAPI` return `*Deps`; `BootstrapHUB` returns `*HubDeps`) and hands the struct to `web.NewServer`. The single shared `NotificationManager` must come from `Deps` — constructing a second one breaks SSE delivery.

**Bus abstraction:** `internal/infra/transport/bus.Bus` is the pub/sub contract. Two impls are interchangeable: `redis/bus` (distributed) and `mem/bus` (standalone in-process). There are no regions: `REGION` and the `BUS_*_QUEUE` overrides are gone and channel names are fixed. `bus:` is the traffic the hub relays for agents: `bus:requests:<hub_id>` (API → that hub → agent; one queue per hub, the API reads `servers.hub_id` on every command; standalone's in-process bridge uses plain `bus:requests`), `bus:responses` and `bus:events` (hubs → API). `hub:` is traffic with the hubs themselves: `hub:requests` (hub → API, today `server.verify`), `hub:responses:<hub_id>` (API → the asking hub) and `hub:broadcast` (API → every hub, today `server.revoked`). Each channel has its own subscription and goroutine, so agent traffic never delays a hub's question. One Redis serves one hosted Winterflow (every API replica and every hub).

**Layering** is hexagonal: `internal/domain/{model,port,usecase,service}` (transport-agnostic business logic) over `internal/infra/{db,transport,orchestrator,cert}` (adapters), with `internal/app/{web,agent}` as the delivery layer. Persistence is sqlc over `database/sql` (`internal/infra/db`, econumo's pattern), SQLite (`modernc.org/sqlite`) or Postgres (`pgx/v5`, simple protocol, session pinned to UTC) chosen by the `DATABASE_URL` scheme in `db.Open`, which also runs the forward-only migrations (`internal/infra/db/migrations/{sqlite,pgsql}/<version>_<name>.sql`; each runs in one transaction with its `schema_migrations` row, Postgres runs are serialized by an advisory lock, and a Bun-era `bun_migrations` table is adopted once, then dropped by `0009_drop_bun_tables`; downgrading to a Bun build is unsupported). SQL is written per engine, never in Go: each repository (`internal/infra/db/repository/<aggregate>/`) has `repo.go` (port methods + hydrate against `sqlitegen` row types behind a private `querier`), `sqlite.go` (passthrough) and `pgsql.go` (struct conversion from the identically shaped `pgsqlgen` types). Transactions: `Tx.WithTx(ctx, fn)` (nested calls use savepoints); inside `fn` every query must use `Tx.Querier(ctx)` with `fn`'s ctx — SQLite has a single connection, so the outer ctx deadlocks. **Adding a query:** the same `-- name:` in `internal/infra/db/sqlc/query/sqlite/<file>.sql` and `query/pgsql/<file>.sql`, `make sqlc`, then the method on the repo's `querier` and both shims (add the new type pair to `sqlc/shapes_test.go`, which fails to compile if the two engines' types differ). **Adding a migration:** the next 4-digit sequence number, `NNNN_<name>.sql`, identical in `migrations/sqlite` and `migrations/pgsql` (comment-only when one engine has nothing to do; `-- migrate:foreign_keys=off` as the first line for a SQLite table rebuild), then `make sqlc`. Keep `.sql` files ASCII; never edit `sqlc/gen`. Repository tests use `dbtest.Open(t)` and run on Postgres under `make test-pg`.

**Orchestration:** the agent deploys apps via the `docker compose` CLI (not the Docker SDK), in `internal/infra/orchestrator/docker_compose`. Each app lives in `{AGENT_DATA_DIR}/apps-data/{appID}/` — a git repository (go-git) that IS the deployment: compose runs in it directly, interpolating `${VAR}` from the committed `.env` (+ gitignored `.env.secrets`, materialized from the ECIES-encrypted committed `secrets.json` at deploy). `{AGENT_DATA_DIR}/apps/` holds human-readable `{slug}` symlinks. Every save/rename is a commit; rollback restores an old tree as a new commit and redeploys. History is unlimited. Git-sourced apps additionally clone their upstream into a gitignored `source/` (SHA pinned in the committed `source.lock`, so rollback restores the source position too), run compose against the repo's compose file, and can auto-update via an agent-side poller.

**x-winterflow:** the compose block every app may carry, parsed once by `internal/domain/compose/xwinterflow` (`Parse(ModeApp|ModeTemplate, files...)`, reading the same YAML trees as `recipe.ParseComposeNodes`): `expose` (`container`, `port`, `protocol` http|tcp|udp, id `<container>:<port>/<protocol>`), `variables` (`required`, `encrypted`, `pattern` RE2 <=512 B matched whole, `description` <=1000 B or the YAML comment above the first `environment:` key; default = that key's body literal, never for a secret; names `^[A-Z][A-Z0-9_]*$`, `WF_*` and `COMPOSE_PROJECT_NAME` reserved), `overrides.services`, `files`, `backups`; unknown keys are errors; YAML aliases and merge keys (`<<: *anchor`, `<<: [*a, *b]`) are expanded once by `recipe.DecodeFiles` (a mapping's own keys win, an earlier merged mapping wins; capped at `recipe.MaxExpandedNodes`, 100 000 nodes per file: past it, an alias inside its own anchor, or a merge of something that is not a mapping, the file reads as not valid YAML), so merged environments declare their variables like literal ones; a non-external volume with a literal `name:` warns in an app and fails a template. Save-app 400s on an invalid block, a missing required value (not for a draft: `CheckDraftValues`), a plain value failing its pattern or holding `$`, a secret variable sent plain, two entries pinned to one port (a pin for an entry the compose file no longer has is dropped, by the API and the agent alike), and an ingress `expose` that is not an http entry (a git-sourced app's block is checked by the agent). Host ports: allocated by the agent (`syncPorts`, `ports.go`) at save (drafts too), rollback and source update from `EXPOSE_PORT_RANGE` (default 20000-29999) under one server-wide lock with an in-memory index (built from every config.json on first use, which `ensurePortIndex` forces before a save or rollback rewrites one; the first app to hold a port keeps it when two claim it, with a warning; pruned in `forgetApp`), stored in the committed `.winterflow/config.json` under `ports` (`{"app:8080/http":{"host":20013,"pinned":false}}`); a save's config `ports` carries the pins (no key keeps them); ports the app holds are never probed, new ones get a listen probe; a pin another app holds is `ErrPortTaken`. At every deploy (`composeUp`, `renderDeployEnv`) the agent checks the values again (secrets after decryption) and writes the gitignored `.winterflow/compose.winterflow.yml` (`xwinterflow.Render`: `NAME: ${NAME}` in each service whose environment has a declared variable with a value; overrides with lists under `!override`, environment merged; expose ports `127.0.0.1:<host>:<port>` or `<host>:<port>/<proto>`), passed as the last `-f` by `composeArgsFor` and `run.sh` but never to `compose down`; every other commit (a draft save, a rollback, a source update) re-renders it best-effort (`refreshComposeOverride`), and a value error writes it without the variables' lines, so it never names a service the compose files no longer have. `IngressDomain` takes `expose` (resolved by `BuildConfig` to `127.0.0.1:<host>`) or `upstream_port`, exactly one; a source update (the poller's `AfterSourceUpdate`, `app.control` update) reloads the ingress, since it can move expose ports. `.env.secrets` quotes every value with `$` escaped. `app.get` returns `declared_variables` and `expose` (host port, bind, pinned) for the editor's variables form and Ports panel; the form blocks a save only for a missing required value (never a draft) or a `$` in a plain one, while a pattern mismatch is a hint (the server alone checks the pattern).

**Monitoring (metrics):** the agent/standalone runs `appagent.StartMetrics`: a `server.metrics` event every 60 s built from procfs/sysfs/cgroupfs reads (`internal/infra/sysmetrics`, no forks; containers come from the status reporter's `StatusSnapshot`, never a second `docker ps`) plus an hourly `ScanDisk` (`docker system df -v`, 5-min deadline). The model, tiers and rollup math live in `internal/domain/metrics`. The API's events sink writes tier-1 rows into `metric_samples` (insert-or-ignore; app rows only for apps the API knows on that server) and keeps the latest host sample in memory (`LatestStore`); `runMetricsMaintenance` (wired in `WireCore`) rolls up 1→10→20→120→480 every 10 min and prunes per tier hourly. Charts are pulled (`/api/v1/metrics/*`), never pushed over SSE. `METRICS_ENABLED=false` switches the whole pipeline off.

**Auth:** `go-pkgz/auth`. Local email+password is the always-on default (`internal/app/web/auth/local.go`, bcrypt in `user_credentials`); login is verify-only — accounts come from `POST /api/v1/auth/register` (fresh instance = one-time claim step creating the admin + the org; distributed self-signup gated by `REGISTRATION_ENABLED`, own org per registrant) or from any member at `/org/members`. Orgs carry name/icon/color (`org/get-organization`, `org/update-organization`). Google OAuth is optional (client id/secret pair, distributed only). JWT-protected `/api/v1/*` routes; personal access tokens (`wfp_…`, SHA-256-hashed at rest, `pkg/pat`) accepted as `Bearer` (via `internal/app/web/middleware/patauth`) or Basic-auth password, managed at `/user/tokens`. No roles: every member of an org may do everything in it (manage members — except removing themselves — register servers, mutate registries/networks/volumes, update the agent, the full app lifecycle). Authorization is authentication plus org ownership of the addressed server (`webutil.RequireServerAccess`). `organization_users.role` is still written (`owner` for an org's creator, `admin` for accounts created in it) but never read. mTLS for hub↔agent.

## Security, stability, and resource invariants

Winterflow ships to small always-on home servers — think mini-PCs and Raspberry Pi-class boards: few cores, possibly ARM, often fanless, thermally constrained. Don't assume any particular CPU, core count, or architecture; assume the weakest plausible box. Idle CPU burn, unbounded growth, and missing authorization are bugs, not polish. A 2026-08 full audit established these rules — keep them when adding code:

**Security (fail closed):**
- A `server_id` from a request is NOT authorization. Every server-addressed route must verify org ownership before dispatching: `webutil.RequireServerAccess` (backed by `ServerRepository.UserOwnsServer`); the app handlers' `authorize` and the docker handlers' `caller` helpers do this — reuse them. The guard denies when unwired (nil), and tests assert 403 per route.
- bcrypt-priced endpoints (login/register) sit behind the per-IP limiter in `internal/app/web/middleware/ratelimit`; put any new expensive unauthenticated endpoint behind it too. The client IP comes from `internal/app/web/middleware/realip`, which honours only the last `X-Forwarded-For` entry (the hop the local proxy wrote; `X-Real-IP` is ignored because a plain reverse proxy passes a client's through) and only when the direct peer is loopback; the Caddy snippet sets it with `header_up X-Forwarded-For {client_ip}` (never use chi's `RealIP`: it trusts any client's header).
- Secret values never leave the agent (mask with the `<encrypted>` placeholder; secret files 0600). Docker/git CLI args are always `[]string` — never build shell strings; user-supplied paths go through `safeRel`, app ids through `filepath.Base`.

**Stability (months of uptime between restarts):**
- Every network operation needs a deadline. The standalone command pipeline is drained by ONE goroutine (`InProcessBridge`), so a single unbounded hang wedges all app management until restart — see `ensureSource`'s 5-minute timeout for the pattern.
- Channel hygiene: close and send must be serialized by the same lock (see `mem/bus`); pump goroutines select on `ctx.Done()` for every blocking send; concurrent writes to one gRPC stream are forbidden — use the per-agent send mutex (`hub.agent.send`).
- Per-app in-memory bookkeeping must be pruned on app deletion (`Repository.forgetApp`).

**Resources (idle cost near zero):**
- Never exec per app in polled paths — process forks (docker/compose/git) are the expensive unit on target hardware. Status collection is ONE `docker ps --all` grouped by the compose project label (`dockerPSByProject`); keep that shape.
- App git histories are unlimited and append-only: anything derived from a history walk must be cached keyed by HEAD (see `commitCount`); source polling skips fetch/checkout work when the upstream hasn't moved and fetches only the configured branch.
- Fan out SSE/notifications only on change (`status.Cache.SetAppStatus` returns `changed`), never unconditionally per tick.
- The embedded ingress carries a predefined per-client-IP throttle (in-repo Caddy module `winterflow_rate_limit`, `INGRESS_RATE_LIMIT_RPS`/`_BURST`, default 50/100, 0 disables) plus header/idle timeouts — new ingress routes must stay behind it (it's prepended to both servers in `BuildConfig`).
- `scripts/install.sh` owns operational limits: journald namespace `winterflow` with rotation caps, Docker container-log rotation, and unit `CPUQuota`/`MemoryMax`. After editing it, run `bash scripts/install_test.sh` (uses `--dry-run`, no root needed).

**Frontend:** `web/src/components/ui/` is intentionally vendored shadcn/ui — never delete its components (or their package.json deps) as "dead code", even when unimported.
